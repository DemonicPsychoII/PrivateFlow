# Test coverage matrix

Every feature and configuration of Private Flow, how it is verified and where. Linked from [VALIDATION.md](VALIDATION.md), which holds the measured baselines.

Levels, cheapest first:

- **Entry point**: `scripts/verify.ps1 -Tier pure [-Parallel <n>] [-Filter <job>[,<job>...]] [-CheckDeterminism] [-Seed <n>]` (Windows PowerShell 5.1 or PowerShell 7, also on Linux) runs every check as a job in its own process, with its own temporary and output folders, up to `-Parallel` jobs at once (default: processor cores). Jobs declare what they occupy: processor jobs run as wide as their cores allow, GPU jobs up to `-GpuSlots`, desktop jobs (foreground and clipboard) up to `-DesktopSlots`, one per Windows session. It writes `report.json` (step, result, start, duration, log, error log, result file and screenshots per job; wall clock, job time and the last sequential time) and prints one `RESULT: PASS|FAIL` line with every failure and its log above it. `-CheckDeterminism` runs the jobs one at a time and then in parallel with the same seed and fails when a job's result differs. The engine and desktop tiers follow with the Windows test VM.
- **Pure**: `tests/PrivateFlow.Tests` (run by `scripts/build.ps1`, also in the Linux CI). The checks run in 53 named groups, one file per area (below; `--list` names them); a failed check is reported and the run goes on, an exception ends only its own group, and the run ends with every failure and its group. `--filter <group>[,<group>...]` (`*` as a wildcard) runs a subset; every group sets up its own data folder and state, so each one runs alone, in any order or in parallel processes. `--result <file.json>` writes the result, checks, failures and duration per group.
- **Engine**: gated app modes against the real whisper.cpp worker, in isolated data folders (`PRIVATE_FLOW_DATA_DIR`): `--transcribe-file` (`scripts/smoke-test.ps1`), `--verify-workspace` (`scripts/verify-workspace.ps1 -Name <name>` runs it from the packaged build with a data folder under `artifacts\<name>`), `--evaluate-dictation` (`scripts/dictation-eval.ps1`), `--evaluate-meeting` (`scripts/meeting-eval.ps1`; `-Mode final` scores the live preview and the final pass, `-Mode oracle` the recognizer's ceiling; `-Title`, `-DictationVocabulary`, `-Corrections` and `-MeetingModelPath` select variants).
- **Desktop**: `--verify-overlay`, `--verify-insert` (own fixture window only; both, and the fixture, run only with an isolated `PRIVATE_FLOW_DATA_DIR`, which `full-eval.ps1` sets) and `scripts/ui-smoke-test.ps1` (UI Automation patterns, no keys). They take the foreground and the clipboard, so `full-eval.ps1` runs them only with `-DesktopChecks`.
- `scripts/full-eval.ps1` runs all of them and prints one PASS/FAIL line, the accuracy headline and the six meeting goal lines (VALIDATION.md); `-Full` adds every backend and model, the oracle and the vocabulary run of the recommended setup. Local only; nothing of it is in `.github/workflows`.

## Publication and update checks

- `publication-leaks`: every tracked text file is checked for private host suffixes, private IPv4 ranges, personal email addresses and concrete Windows profile paths. Generic placeholder paths, loopback and noreply addresses pass. Tracked non-ASCII PowerShell scripts must have UTF-8 BOMs.
- `public-export`: temporary Git repositories exercise the real exporter in Windows PowerShell 5.1 and PowerShell 7: committed content rather than dirty files, no history or workflows, rejection of nonempty targets, and rejection of each private-detail pattern and the internal runner label outside workflows. Like the other PowerShell execution checks, it runs on Windows; the tracked-text and BOM gates also run on Linux.
- `evaluation-encoding`: Windows PowerShell 5.1 and PowerShell 7 parse the evaluation scripts and run Spanish negation marking, checking accented literals without executing audio or downloading assets.
- `release-updates`: fake HTTP responses cover anonymous source selection, legacy-token fallback, numeric stable-version ordering, release assets, matching manifest size/version/hash and optional digest, drafts, pre-releases, empty/malformed metadata, offline/cancelled checks, 404 and rate limits. Per-user URL configuration is read from temporary files.
- `update-installer`: Windows PowerShell 5.1 and PowerShell 7 run the real installer functions with fake HTTP commands and isolated data. Valid bytes pass; wrong size, SHA-256, digest and manifest version fail before installation. A versioned executable fixture covers newer, equal and older versions and `-Force`, on both release and server-fallback paths. Token setup stores URLs and a DPAPI token, retains the token on an empty prompt, and a token without URLs chooses releases with the same explanation and recovery command as the app notice. Missing releases (HTTP 404) get an explanatory cause. No real network, installation, microphone or key input is used.
- `settings-persistence` covers the empty endpoint default, notice for a missing legacy key, and preservation of saved endpoints. `concise-configuration` checks that an empty endpoint fails before any request. API notes keep their existing extractive fallback coverage.

A real public release and an end-to-end update from it have not been verified yet.

## Own recordings (local only)

Your own meetings can be scored locally. They are private conversations: they stay outside the repository, and the suite reports counts only (no transcript text, missed words or segment text in reports, summaries or the console). Without a recordings folder the step is skipped, as on CI and other PCs.

- Give the folder with `-Recordings <folder>` to `scripts\meeting-eval.ps1` or `scripts\full-eval.ps1`, or set `PRIVATE_FLOW_EVALUATION_RECORDINGS`. `meeting-eval.ps1 -Scenario none -Recordings <folder>` runs only the recordings; `full-eval.ps1 -Full` runs them with the recommended GPU setup (step "Own recordings").
- Add a recording: create a folder per meeting, for example `2026-11-16-meeting`, and copy the meeting's folder from `%LOCALAPPDATA%\PrivateFlow\meetings\<id>` into it as `meeting` (its `meeting.json` and the `mic-*.wav` and `system-*.wav` chunks, so retain the audio or copy it before the meeting is finished).
- Add a reference: `reference.txt` in the recording's folder, one utterance per line of what the people said, in order, critical items (times, numbers, names, negations) in square brackets, for example `We meet at [12:30], [not] on Friday.` Then the recording is scored for accuracy (words and critical items).
- Without a reference, the newest `final-pass-*.meeting.json` in the folder (a meeting record a build produced, such as `final-pass-1e44c17.meeting.json`) is the comparison, reported as agreement with that pinned transcript: drift between builds, not accuracy.
- Each run finishes a temporary copy in the isolated data folder the way **Finish transcripts** does, with retention off, and reports the final status, the time to finish, whether the progress reached 100 % and how many audio files the copy still holds afterwards; the copy is then deleted. The recording folder itself is only read.
